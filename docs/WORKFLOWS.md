# 작업 유형별 추천 흐름

도구는 수단입니다. **제공된 실제 요구사항이 먼저**이고, 불필요한 설치·설정에 시간을 쓰지 않습니다.

## 유형 A. 데이터 파일 여러 개로 보고서 작성

1. README·입력 목록·열 정의·산출물 형식을 확인합니다.
2. inventory.py, data_profile.py로 기초 구조를 확인합니다.
3. 서로 다른 표를 연결해야만 한다면 join_audit.py로 관계와 예상 행 수를 조사합니다.
4. 명확한 공통 키가 있으면 merge_tables.py를 사용하거나 직접 코드를 수정합니다.
5. 분자·분모·기간·단위를 명시하고 quality_report.py용 JSON 설정을 작성합니다.
6. 보고서에서 몇 개의 값은 원본 행을 이용해 독립 검산합니다.
7. 저장된 출력의 형식과 파일 경로를 확인하고 미검증 범위를 남깁니다.

**주의:** 자동 생성되는 것은 Markdown 보고서입니다. PDF·Word·프레젠테이션·차트가 요구된다면 해당 환경의 도구를 추가로 사용해야 하며 기본 제공 기능이라고 주장하지 않습니다.

## 유형 B. CSV 변경 원인 확인

1. 이전/이후 파일이 같은 업무 대상·같은 기준인지를 확인합니다.
2. 식별키를 정합니다. 키가 중복되면 먼저 그 의미를 확인합니다.
3. compare_tables.py로 추가·삭제·수정된 행 수를 확인합니다.
4. 변경 열을 기준으로 원본 표본과 직접 대조하고 의미를 설명합니다.
5. 데이터 정규화·삭제·보정은 별도 승인을 받아 수행합니다.

## 유형 C. 기존 웹 앱이나 API 수정

1. 제공 프로젝트의 실행법·의존성·포트를 먼저 확인합니다.
2. 문제를 재현하는 최소 테스트를 실행합니다.
3. 변경해야 할 코드만 수정하고 기존 구조를 보존합니다.
4. 동작하는 로컬 HTTP URL이 있을 때만 http_smoke.py를 이용합니다.
5. HTTP 상태 코드만이 아니라 실제 화면·응답 내용·콘솔 오류도 확인합니다.
6. 외부 배포·네트워크 연결은 환경 정책이 명시적으로 허용하지 않으면 하지 않습니다.

## 유형 D. 업무 자동화·Python 코드 수정

1. 입력→처리→출력의 실제 동작과 기대 결과를 정합니다.
2. 정상 입력 하나, 잘못된 입력 하나, 경계 조건 하나를 테스트로 만듭니다.
3. 최소 구현 후 해당 테스트와 기존 회귀 테스트를 실행합니다.
4. 오류가 나면 실제 오류 메시지와 재현 방법을 먼저 확인합니다.
5. 실행하지 않은 테스트나 환경이 허용하지 않는 기능은 완료로 표시하지 않습니다.

## 유형 E. 문서·제안서·설명 자료

1. 목적·읽을 사람·출처·형식·평가 기준을 확인합니다.
2. 확인된 수치와 해석을 분리합니다. 수치의 분모·기간·단위를 병기합니다.
3. 작성 후 원자료와 표 수치를 대조합니다.
4. 표나 그림이 있으면 표시 상태까지 직접 검토합니다.
5. 요구된 산출물 확장자가 Markdown 이외라면 해당 형식 도구가 제공되는지 확인합니다.

## 어느 경우에도 공통

- 요구사항 하나를 실제 출력·테스트 증거 하나와 연결합니다.
- 임의의 지표·정답·예외 조건을 만들지 않습니다.
- 처리할 수 없는 제한은 실패 원인과 함께 밝힙니다.
- 변경·선택 이유를 기록할 필요가 있을 때만 templates/ 문서를 사용합니다.

## 유형 F. JSON API·자동화 결과 검증

1. 요구된 응답 필드와 필수 자료형을 확인합니다.
2. 필요한 필드를 JSON 계약 설정 파일에 명시합니다.
3. scripts/json_structure_check.py로 필드 누락·타입 오류·추가 필드를 검사합니다.
4. JSON 구조 검사 통과와 **실제 응답 내용의 의미적 정확성**을 구분합니다.
5. 중요 결과는 호출 조건과 실제 입력에 따라 별도 테스트합니다.
